# McpGo — эксплуатация и восстановление

Актуальность: 06.11.2026. Все команды ниже предназначены для Mac владельца; **не** запускайте на другом хосте без проверки путей.

## Требования

macOS 14+, arm64 для нативной сборки, Xcode/macOS SDK, Node.js для сервисов, Python 3 для обмена агентами, личный Google Chrome, Playwright MCP и OpenAI tunnel-client. LaunchAgents выполняются в `gui/$(id -u)` обычного пользователя, а не системного root-контекста.

## Папки

- Физический путь проекта: `<INSTALL_ROOT>`. Точка входа после ребрендинга: `McpGo.app`; старое `MCP Hub.app` оставлено как alias совместимости.
- Активные LaunchAgent plist: `~/Library/LaunchAgents`; шаблоны: `launchagents/`.
- Исполняемый скрипт терминального туннеля: `~/Library/Application Support/ChatTerminalHub/run-tunnel.sh`, с доступом владельцу.
- Агентская SQLite БД: `messaging/data/messages.sqlite3`.
- Данные AutoSend: `~/Library/Application Support/MCPHub/AutoSend` (старый идентификатор сохранён).
- Фактические логи — в путях `StandardOutPath`/`StandardErrorPath` соответствующих plist.

## Автовосстановление туннелей (2.0.4)

После успешного запуска Terminal или Playwright через Dashboard
параметр desired сохраняется локально в
~/Library/Application Support/McpGo/tunnel-recovery-state.json (0600).
Нажатие «Остановить» отключает контроль. Поле recovery в
GET /api/status показывает состояние каждого канала.

Проверки происходят раз в 15 секунд по приватным loopback health URL
в Application Support. Три последовательных неудачи liveness
могут вызвать перезапуск только соответствующего tunnel-client.
Готовый, но не ready процесс не убивается: клиент самостоятельно
повторяет подключение. После шести неудач срабатывает circuit breaker.
Состояние браузера, PTY и worker не затрагиваются.

После пропажи ответа агента: mcpgo_recover, затем job_status и
job_result. Не повторять команды с неизвестным результатом.

## Стандартная диагностика

```bash
curl -fsS http://127.0.0.1:12847/health
curl -fsS http://127.0.0.1:12848/health
launchctl list | grep -E 'com.chatterminalhub|com.mcphub'
launchctl print "gui/$(id -u)/com.chatterminalhub.tunnel"
curl -fsS http://127.0.0.1:8969/api/status
curl -fsS -H 'X-MCPHub-Client: native' http://127.0.0.1:8971/api/status
curl -fsS -H 'X-MCPHub-Client: native' http://127.0.0.1:8972/api/status
```

Затем проверьте реальные read-only инструменты **из ChatGPT**: `terminal_exec` и `browser_tabs(action=list)`. Наличие процесса или открытого порта не доказывает работоспособность Secure MCP до ChatGPT.

## Исправление терминального туннеля

При коде `127` проверьте `launchctl print`, активный plist и stderr. Проблема 06.11.2026: LaunchAgent запускал `run-tunnel.sh` напрямую с Desktop, что приводило к ошибке открытия файла, хотя вручную скрипт работал. Теперь Dashboard обеспечивает миграцию: скрипт копируется в Application Support, `ProgramArguments:0` обновляется, `WorkingDirectory` Desktop удаляется, plist проверяется и служба перерегистрируется.

Используйте кнопку рестарта McpGo; для существующего процесса допустимо:
```bash
launchctl kickstart -k "gui/$(id -u)/com.chatterminalhub.tunnel"
```
Если изменён сам plist, может потребоваться `bootout` + `bootstrap`. Это может прервать действующий MCP доступ, поэтому делайте только когда можно восстановить управление. Не подставляйте путь в индекс `ProgramArguments:1`: единственный элемент — индекс 0.

## Ошибки Playwright

Проверьте `chrome://inspect/#remote-debugging` (Allow remote debugging for this browser instance), запуск обычного Chrome, процессы backend :8931, proxy :8940 и browser tunnel. Не запускайте отдельный Chromium. `PlaywrightHub` использует уже открытые пользовательские вкладки. Проверяйте end-to-end через реальный `browser_tabs`.

## Ошибки AutoSend

Проверьте `com.mcphub.autosend`, `127.0.0.1:8972/api/status`, подключение к `:8940/mcp` и точный URL разговора. Состояние busy — повод дождаться нового интервала; unknown после возможного клика не повторять автоматически. Расписание и историю не удалять ради проверки. Отправка в рабочий чат без согласования не является безопасным тестом.

## Резервные копии, обновление, откат

1. Сохраните bundle, существующие plist, messaging SQLite (для согласованного бэкапа — после остановки writers либо SQLite backup API), данные AutoSend и настройки туннелей.
2. Проверьте линтеры, unit-тесты, Swift сборку, подпись, синхронность встроенных SKILL.md.
3. Обновите подписанный bundle и перезапустите приложение. Перезапускайте службы по одной, проверяя реальные read-only вызовы.
4. При сбое верните bundle/plist из backup, сохраните данные пользователей и не перезаписывайте их старым форматом.
5. Менять старые системные ID без отдельного migration plan запрещено: они составляют часть действующего конфигурационного контракта.


## AutoSend Dev 2.0.5: безопасная проверка отправки

- ChatGPT наблюдается через существующий Playwright MCP в личном Chrome.
  Перед вводом текста нужны два согласованных снимка готовности; прямо
  перед Send состояние проверяется ещё раз.
- Лёгкий MutationObserver сохраняет только счётчики и время изменений.
  Ни переписка, ни скриншоты не добавляются в диагностический журнал.
- Состояние verifying означает, что Send мог быть нажат. Reconciliation
  выполняет только чтение, без нового Send, максимум 8 минут с задержками.
- При unknown задача останавливается, но сохраняется исходная квитанция.
  Кнопка «Проверить ещё раз · без отправки» запускает ещё две минуты
  read-only наблюдения. Старые unknown без сохранённой квитанции требуют
  ручной проверки разговора.
- Подробности в журнале: Send мог быть нажат, очистилось ли поле ввода,
  найдена ли новая пользовательская реплика и сколько было проверок.
- Watchdog обновляет вкладку только после явной устойчивой ошибки
  соединения. Долгая работа без такой ошибки не прерывается.
  После reload две согласованные проверки готовности обязательны.
- Для обновления работающего AutoSend на Mac сначала убедиться, что нет
  checking, sending или verifying. Перезапускать только службу
  com.mcphub.autosend, не терминальный и не браузерный MCP-сервер.


## AutoSend Dev 2.0.6: защищённый Send и независимые чаты

Перед отправкой McpGo дважды проверяет готовность, вводит текст в поле
личного Chrome и сохраняет durable action ID. Затем один guarded
browser_evaluate одновременно проверяет актуальность URL, редактора,
черновика, ответа и кнопки и выполняет ровно один DOM click. Действие
сериализовано MCP-прокси и не повторяется при тайм-ауте. Успешный клик
сам по себе не является подтверждением доставки; нужна новая
пользовательская реплика, подтверждённая только read-only проверкой.
При достоверном отказе до клика можно продолжить по интервалу;
при неопределённом ответе нельзя нажимать Send повторно.

Для событий MutationObserver хранит только счётчики, время изменений
и краткоживущих подписчиков. При проверке занятого чата browser_evaluate
может ожидать событие до 1300 мс (в штатном watchdog — 1000 мс).
Если событие не пришло, остаётся обычная проверка. Это
событийно поддерживаемое наблюдение, а не непрерывный CDP-канал.

GET /api/status отдаёт conversations с отдельным состоянием каждого
разговора: READY, WORKING, RECOVERING, VERIFYING_SEND, UNKNOWN, PAUSED.
Они вычисляются из уже сохраняемых задач в tasks.json. Неизвестная
отправка в одном чате блокирует новые Send в этом разговоре,
но не блокирует другие чаты. Общий Chrome всё равно сериализуется
на уровне инструмента.

Автономная проверка: node --test autosend/tests/*.test.mjs.
Симулятор в autosend/simulated-browser.mjs исполняет реальные
pageInspection и guardedClick внутри Node VM. Он воспроизводит обрыв
после клика, смену вкладки, зависшую генерацию, задержку DOM,
несовпадение редактора и четыре независимых чата без браузера
и без реальной отправки. Приёмку в живом ChatGPT следует проводить
в отдельном тестовом разговоре: симуляция не заменяет проверку React.

Для переключения Dev-runtime сначала убедиться, что нет статусов
checking, sending, verifying. Затем собрать Dev, отдельно перезапустить
только com.mcphub.autosend и проверить GET /api/status.
Не изменять установленный релиз и MCP-туннели.


## AutoSend Dev 2.0.7: длинные виртуализированные чаты

Новый пользовательский блок в ChatGPT может заменять старые DOM-узлы;
например 6 видимых реплик до Send превратятся в 5 после него. В длинном
чате текст отправки может дословно совпадать с предыдущим. Поэтому
увеличение количества DOM-реплик и смена неустойчивых ID больше не
являются единственными механизмами подтверждения.

Виртуализированная реплика может считаться подтверждённой при
совпадающем последнем пользовательском блоке в правильном разговоре
и наличии ВСЕХ дополнительных признаков после сохранённого клика:
редактор очистился, DOM-наблюдатель увидел вставку пользовательского
элемента и наблюдалась новая активность ответа. Сам текст, очистка
поля или Stop по отдельности никогда не подтверждают отправку.
Положительные признаки сохраняются между проверками; для старой
попытки их можно восстановить из журнала строго по task_id/времени.

Если браузер и после этого не даёт достаточного доказательства,
задача остаётся unknown и отправка не повторяется. Пользователь
может либо перепроверить страницу без Send, либо вручную подтвердить
реально увиденную реплику. Ручное подтверждение записывается отдельно
и оставляет расписание выключенным. Это НЕ серверная гарантия
доставки, а явно указанная пользовательская проверка.
