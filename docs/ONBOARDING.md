# McpGo — автоматический мастер первого запуска

Статус: реализован в публичной копии McpGo; remote provisioning проверен на mock OpenAI Platform, но не на действующих ключах пользователя. Реальные удалённые ресурсы не создавались.

## Пользовательский сценарий

1. Открыть McpGo.app или «Запустить McpGo.command». Лаунчер открывает интерфейс; ничего не ставит без согласия.
2. «Первое подключение» → системный preflight: macOS 14+, arm64, Node/npm, Python, tunnel-client, Playwright. Кнопка установки зависимостей выполняет npm ci только после подтверждения.
3. Ввести Platform Organization ID и при необходимости ChatGPT Workspace ID. Для создания нужны Tunnels Read + Manage. Для runtime нужны Tunnels Read + Use.
4. Создать два туннеля автоматически либо импортировать два существующих Tunnel ID. Поиск и создание выполняются только в явном scope.
5. Ввести restricted runtime API key. SwiftUI сохраняет его в macOS Keychain, не в исходниках или YAML.
6. Настроить локальные HTTP профили через официальный tunnel-client init. Terminal target — приватный маршрут OneShot на 127.0.0.1:12848; Browser target — Safe Proxy 127.0.0.1:8940/mcp.
7. После подтверждения — установка пользовательских LaunchAgents. Никакого sudo, никакой автоматической замены чужих labels.
8. В личном Chrome вручную разрешить CDP. Мастер не обходит системное согласие.
9. Открыть https://chatgpt.com/plugins → «Добавить» → «Добавить пользовательский сервер MCP». Создать два отдельных плагина (McpGo Terminal и McpGo Browser), выбрать для каждого Connection: Tunnel и его Tunnel ID, выбрать «Без аутентификации», подтвердить предупреждение и создать плагин; ChatGPT автоматически показывает окно «Подключить», которое нужно подтвердить (искать плагин во вкладке «Личные» не нужно). Официальной прямой ссылки для открытия формы нет, поэтому только переход на страницу Plugins. На шаге 6 находится свёрнутая иллюстрированная инструкция: сначала выбор «Добавить пользовательский сервер MCP» (assets/onboarding/chatgpt-plugin-menu.png), затем заполнение формы (assets/onboarding/chatgpt-server-form.png) и отдельная подсказка об автоматическом окне подтверждения подключения (assets/onboarding/chatgpt-connect-confirmation.png). Для встроенных серверов McpGo без собственного OAuth в настройке MCP указан вариант «Без аутентификации», при этом доступ к Tunnel по-прежнему проверяется OpenAI.
10. Выполнить read-only диагностику MCP и tunnel-client doctor, затем проверку реального инструмента из ChatGPT. Локальные тесты не подменяют последнюю проверку.

| scripts/launch-macos.sh | Только запуск интерфейса |
| terminal/stateless_server.js | Terminal MCP приватный route |
| playwright/restricted-proxy.mjs | Browser MCP с ограничениями инструментов |
| onboarding/tests/test_setup_engine.py | Регрессия provisioning, unknown outcome, state и permissions |

## State, безопасность и идемпотентность

Файл состояния: ~/Library/Application Support/McpGo/Onboarding/state.json.

Права: 0600, каталог 0700, запись через atomic replace. Привязан к физическому install root. Содержит случайный ID установки, фазу, tunnel IDs, происхождение каждого ресурса и pending remote operation. API keys в него не попадают.

Перед созданием туннеля выполняется admin tunnels list --json в точном org/workspace scope. Имя туннеля уникально для установки. Если create завершился ошибкой после возможного обращения к серверу, pending становится unknown. Повторный вызов сначала повторяет list; при отсутствии созданного ресурса новый create блокируется до ручной проверки в Platform. Это предотвращает бессмысленные дубликаты.

Важные Keychain services совместимы со старой установкой. До любой записи ключа мастер проверяет принадлежность действующих LaunchAgents через setup_macos.py --check. Если на Mac уже есть другая установка, профиль не перезаписывается.

Admin key вводится через SecureField, передаётся в отдельный Python-процесс через stdin и далее только во временном environment tunnel-client. Runtime key сохраняется в системном Keychain. Профили содержат ссылку env:CONTROL_PLANE_API_KEY.

Отмена мастера никогда не удаляет уже созданные удалённые туннели; удаление должно быть отдельным явным действием. Ошибки локальной установки не останавливают чужие процессы.

## Действия CLI bridge

| Action | Эффект |
|---|---|
| status, preflight | Read-only, без создания состояния |
| check-ownership | Read-only проверка принадлежности служб |
| discover | Admin Tunnels List с явным scope |
| provision | Подтверждённое создание/повторное использование удалённых ресурсов |
| import | Сохранение двух ID, remote-verified=false |
| verify-remote | Read-only Tunnels Get для каждого ID |
| configure | Профили terminal/browser и local Tunnel ID |
| install-deps | npm ci после подтверждения |
| install | User LaunchAgents после collision check |
| start-local | Явный запуск Terminal либо Playwright через локальный Dashboard |
| verify-local | MCP initialize, notifications/initialized, tools/list, browser_tabs(list) |
| doctor | Проверка terminal/browser через tunnel-client doctor |
| chatgpt-instructions | Записывает факт ознакомления, НЕ устанавливает chatgptVerified |

Вызовы происходят без передачи ключей в command-line arguments; stdout содержит JSON с результатом/ошибкой без raw stderr.

## Устройство профилей

Terminal: профиль chat-terminal-hub с private endpoint OneShot. Browser: профиль mcpgo-browser для команды doctor и локальный tunnel.id, используемый действующим browser launcher.

Локальные профили генерирует именно установленный tunnel-client init, а не вручную написанный YAML. Его текущую справку необходимо проверять после обновлений tunnel-client.

## Проверки и остаточные ограничения

Подтверждены 9 сценариев unit-тестов: идемпотентность, unknown-before-create, recovery, mode import, неверные ID, изоляция разных root, приватные права state, профили и отсутствие ложного ChatGPT verification. SwiftUI typecheck проходит на arm64 macOS.

Реальное создание в OpenAI Platform, права определённого workspace и пользовательское подтверждение custom MCP в ChatGPT не выполнялись. На Mac с действующей другой установкой мастер блокирует вмешательство. Полноценная E2E-приёмка должна проходить на отдельном чистом Mac либо после явной миграции действующих служб.

См. также GETTING_STARTED.md, SECURITY.md, PACKAGING.md, VERIFICATION.md, PUBLIC_RELEASE.md.


## Маркер владельца LaunchAgent

Во время установки scripts/setup_macos.py записывает переменную
MCPGO_INSTALL_ROOT в EnvironmentVariables каждого пользовательского plist.
Это особенно необходимо для терминального туннеля: его ProgramArguments
указывает на Application Support, а не исходный проект. На последующих
запусках установщик сверяет метку с каноническим root; несовпадение означает
конфликт, а не разрешение перезаписать службу.

## CI проверка

Workflow .github/workflows/verify.yml предназначен для нового публичного репозитория. Использует macOS, фиксированный Node 20 и Python 3.11, выполняет unit/integration тесты и SwiftUI typecheck. CI не создаёт OpenAI tunnels и не содержит пользовательских API keys. Пока репозиторий не опубликован, workflow не запускался на GitHub Actions.


## Добровольный выход из мастера

Статус verification означает ожидание настоящего вызова из ChatGPT,
а не завершение. Кнопка «Продолжить без подтверждения ChatGPT» записывает
только wizardDismissed=true. При следующем запуске откроется обзор,
но chatgptVerified останется false. Мастер всегда можно открыть из меню.


## Автоматическая выдача Runtime API Key (Dev Preview)

На шаге 3, после создания двух туннелей, пользователь выбирает
**«Автоматически»**. Используется временный Admin API Key со шага 2
(только в памяти приложения), либо пользователь повторно вводит его.
Кнопка «Найти мои проекты OpenAI» выполняет только read-only
\`GET /v1/organization/projects\`. Пользователь выбирает проект и явно
нажимает «Создать ограниченный ключ и продолжить».

У OpenAI всегда есть системный **Default project**, но он не позволяет
добавлять Service Accounts напрямую. Поэтому мастер **не предлагает Default**
в списке проектов для этой операции.

Основной сценарий не требует заранее созданного проекта: пользователь
выбирает **«Создать проект McpGo»** (вариант по умолчанию) и подтверждает
создание отдельного API-проекта с именем вида McpGo + идентификатор установки.
Для этого нужны права владельца организации. Создание проекта выполняется
только после явного нажатия кнопки — никогда при поиске проектов или запуске
приложения. Список существующих подходящих проектов доступен в отдельном
режиме **«Использовать существующий»**. Если доступен только Default, список
остаётся пустым с понятной подсказкой.

Перед POST проект сравнивается со списком по уникальному имени установки;
при потере ответа создание не повторяется вслепую. Если API запретил
создавать проект (например, нет полномочий владельца), мастер предлагает
доступный обычный проект или ручную настройку. Проекты OpenAI нельзя
удалить — только архивировать; это отдельно поясняется пользователю.

После подтверждения McpGo создаёт выделенные ресурсы (или сверяет их
по стабильному уникальному имени установки):

1. Организационная роль **только** с
   \`api.organization.tunnel.read\` и \`api.organization.tunnel.use\`;
2. Отдельная группа, которой назначается эта роль;
3. Service Account в выбранном проекте **без стартовой роли и ключа**,
   включаемый в группу;
4. Scoped API Key Service Account с двумя указанными scope-правами.
   Dev-ключ запрашивается со сроком действия 90 дней; политика
   организации может потребовать иного срока.

Первоначальная выдача ключа не доказывает, что он уже может работать:
SwiftUI сохраняет одноразово выданное значение **сразу в macOS Keychain**
и отдельно проверяет доступ к обоим Tunnel ID через \`tunnel-client\`.
Организационные роли могут применяться до 30 минут; при задержке
приложение позволяет повторить проверку **сохранённого ключа без
создания нового**. Настройка профилей начинается только после успешного
ответа от OpenAI.

Безопасность и идемпотентность:
- Все POST-запросы выполняются только после явного подтверждения.
- Идентификаторы ресурсов и стадия операции хранятся в 0600
  \`Onboarding/state.json\`, **никогда** сами ключи.
- HTTP ошибки не выводят тело ответа провайдера и никогда не печатают ключ.
- При сетевой неопределённости после POST приложение делает сверку, но
  не повторяет создание ресурса вслепую.
- При успешной выдаче секрет доступен только в одноразовом ответе
  локального stdin/stdout-канала Python→Swift. Swift сразу сохраняет
  секрет в Keychain и не показывает пользователю.
- Если полномочий на Service Accounts, роли, группы или ключи недостаточно
  либо OpenAI отказывает в нужных scopes, пользователь может выбрать
  **«Ввести вручную»**, без автоматического расширения прав.
- По умолчанию не создаётся отдельный OpenAI-проект и не выдаются права
  на модели, ответы и другие API. Создаётся лишь ограниченная роль
  Tunnels Read + Use.

Проверено тестами с фиктивным Admin API: подтверждение, минимальные
права, скоуп ключа, восстановление уже созданных ресурсов, блокировка
двойного выпуска, отказ провайдера и потеря ответа. Живую выдачу
ключа OpenAI нужно проверять **пользовательским нажатием в мастере**;
автоматически при запуске приложения запросы с побочными эффектами
не выполняются.

- https://developers.openai.com/api/docs/guides/rbac
- https://developers.openai.com/api/docs/guides/secure-mcp-tunnels

### Восстановление незавершённого выпуска ключа

Если создание проекта или роли завершилось без подтверждённого результата,
мастер сохраняет только этап и идентификаторы ресурсов, не API-ключи.
При повторном открытии экрана он предлагает сначала выполнить
«Проверить ресурсы OpenAI (без изменений)» с временным Admin API Key.

- Если роль найдена с разрешениями Tunnels Read и Tunnels Use, она используется повторно.
- Если роль не найдена, повторять создание автоматически запрещено.
  Пользователь должен явно подтвердить один дополнительный запрос;
  непосредственно перед POST список проверяется ещё раз.
- Если в предыдущем запуске был выбран системный Default project, мастер
  после подтверждения создаёт отдельный проект McpGo и сохраняет
  связь с предыдущей попыткой. Незавершённое создание роли не забывается.
- Если статус остался неопределённым после повторной попытки, дальнейшее
  автоматическое создание запрещено; используется ручная сверка в Platform.
- Runtime API Key выпускается через документированный HTTP-параметр scopes (массив разрешений), только с правами Tunnels Read + Use. Значение никогда не сохраняется
  в Onboarding/state.json; SwiftUI переносит ключ в Keychain.


### Когда существующая роль не имеет нужных разрешений

Если повторная проверка OpenAI находит роль McpGo, но у неё не ровно
Tunnels Read + Use, мастер показывает недостающие и лишние permissions,
а не блокирует пользователя без объяснения. С явного подтверждения
создаётся **отдельная** роль McpGo Runtime Restricted, содержащая только
две нужные permissions. Оригинальная роль никогда не изменяется и не
удаляется. При неопределённом результате повторного POST этот шаг не
выполняется вслепую: сначала сопоставляется точное имя новой роли.

Если в старой попытке одновременно использовался Default project,
мастер только после согласия создаёт обычный проект McpGo и новую
ограниченную роль. Список ролей и проектов при проверке читается
без изменений на стороне OpenAI. Тесты проверяют оба препятствия вместе.


### Диагностика нестандартного ответа OpenAI Role API (Dev)

По официальному API POST /v1/organization/roles и
GET /v1/organization/roles должны возвращать роль с полями
id, name, permissions. Если после POST роль не подтверждена
валидным идентификатором, McpGo выполняет до трёх GET-проверок
с небольшими задержками, но не повторяет POST.

Когда GET тоже не подтверждает результат, McpGo запоминает только
безопасную техническую метаинформацию: имя операции, GET или POST,
HTTP-статус, имена JSON-полей и их типы, количество точных
совпадений по имени. Содержимое ответа, API-ключи, идентификаторы
ресурсов и имена пользователей не сохраняются и не выводятся.
После повторного открытия мастер предлагает сначала кнопку
«Проверить ресурсы OpenAI (без изменений)», затем раскрываемый
пункт «Диагностика предыдущего ответа».

Разрешения и наличие ID проверяются раздельно. Если права
api.organization.tunnel.read и api.organization.tunnel.use
уже есть, но OpenAI не дал Role ID, это не ошибка разрешений.
Роль не пересоздаётся; предлагается переход к ручному Runtime API Key.
Для совместимости с нестандартными ответами McpGo также распознаёт
role_id или roleId, но только при точном совпадении имени роли,
минимальных разрешений и корректном формате ID.

После каждой неудачной попытки SwiftUI перечитывает локальный
журнал операций, сбрасывает старые флажки и требует новой
read-only проверки перед любой следующей попыткой изменения
ресурсов. Режим «Использовать существующий проект» подчиняется
такому же правилу.


### Если Runtime API Key не сохранился после выпуска

Когда журнал первого подключения содержит status key-issuing, McpGo
уже зарегистрировал проект, роль, группу и Service Account. Повторять
их создание не требуется. OpenAI показывает секрет ключа только один
раз в ответе о создании; запрос списка ключей не восстанавливает секрет.

Теперь мастер сначала показывает read-only проверку Service Account
и существующих ключей проекта. Их количество считается с помощью
GET /organization/projects/{project_id}/api_keys с фильтром
owner_project_access=any и owner.service_account.id. Сами ключи,
их идентификаторы и секреты в интерфейс не передаются.

Если Runtime API Key уже есть в Keychain, используется проверка
существующего ключа. Иначе владелец может явно разрешить выпуск
одного нового ограниченного ключа для подтверждённого Service Account,
который уже принадлежит выбранному проекту. Перед POST в локальный
журнал записывается keyRecoveryAttempted=true; повторные попытки
автоматического создания запрещаются даже при потере ответа.

Новый ключ сохраняется в macOS Keychain и проверяется в обоих туннелях.
Старые ключи приложение не удаляет: прежний мог быть успешно выпущен,
но его ответ был потерян. Отзыв старых ключей пользователь выполняет
отдельно после успешной проверки нового.
