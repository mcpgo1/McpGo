# McpGo — безопасное восстановление соединений

Статус: проект алгоритма, НЕ внедрён. Последняя проверка: 2026-11-08.

## Текущее состояние

- Терминальный туннель: launchd KeepAlive.SuccessfulExit=false, ThrottleInterval=15; только после неуспешного выхода.
- Терминальный server: аналогично; stateless/oneshot: KeepAlive=true.
- Playwright browser, proxy и tunnel: KeepAlive=false. Перезапуск автоматикой не обеспечен.
- Длительные terminal job: отдельные процессы, сохраняемые результаты и heartbeats; job_status, job_recent и job_logs дают восстановление контекста без повторного запуска.
- Браузерный proxy: повтор модифицирующего действия с неопределенным результатом запрещён.
- tunnel-client поддерживает --health.listen-addr и --health.url-file; PID сам по себе не доказывает успешное подключение.

## Предлагаемый supervisor

1. **Изоляция.** Отдельный контроль Terminal Tunnel и Playwright Tunnel без общей блокировки четырех агентов. Запускается только если пользователь завершил настройку и ранее явно включил службу.
2. **Health.** Выбрать для каждого tunnel-client loopback endpoint 127.0.0.1:0; записывать фактический адрес в отдельный файл 0600 с --health.url-file. Опрос раз в 10–15 секунд, таймаут 3 секунды. Отличать локальное здоровье MCP от удалённой доступности инструментов ChatGPT: успешная локальная проверка не подтверждает remote.
3. **Дебаунс.** Один timeout не повод для рестарта. После трех последовательных неудач за 30–45 секунд, исключая сон Mac и отсутствие сети, перейти CONNECTED -> DEGRADED -> RECOVERING. Дать tunnel-client шанс переподключиться самостоятельно.
4. **Минимальное вмешательство.** Перезапускать только конкретный tunnel-client/его LaunchAgent, не трогать терминальные задачи, PTY, пользовательский Chrome, browser actions и соседний туннель. Восстанавливать browser/proxy только при отдельно подтвержденной их неисправности.
5. **Ограниченное восстановление.** Exponential backoff 5/10/20/40/80/120 секунд с jitter 10–20%, не больше шести неудачных запусков за 15 минут. Далее NEEDS_ATTENTION, без crash-loop. Успешные две проверки сбрасывают счетчик.
6. **Auth.** Ошибки авторизации (401/403, отсутствующий/отозванный tunnel ID, нужные права) переводят в AUTH_REQUIRED, без автоматического повтора до действий пользователя.
7. **Сохранение результатов.** После сетевого разрыва сначала job_status/job_recent, читать лог и подтверждать фактический exit_code. Статусы unknown/stalled/queued не означают успех. Не повторять shell-команду или клик из-за потери ответа.
8. **UI и безопасность.** Показывать состояния CONNECTED/DEGRADED/RECOVERING/OFFLINE/AUTH_REQUIRED/NEEDS_ATTENTION/STOPPED_BY_USER, причину, последнюю успешную проверку и следующую попытку. Health только loopback; никакие секреты или содержимое команд в диагностические события.
9. **Поддержка четырех агентов.** Никаких глобальных блокировок терминала; supervisor блокирует только одновременный рестарт одного канала.

## Приемочные тесты

- Отключение и возврат сети, сон/пробуждение, kill клиента с exit=0 и exit!=0, зависший процесс при доступном PID, кратковременное падение backend.
- Недействительные credentials; нет бесконечных запусков.
- Четыре долгих параллельных задания продолжаются при переподключении, результаты доступны по id.
- После неизвестного результата browser click/send не повторяется.
- После шести неудач circuit breaker; ручное восстановление доступно.
- После перезапуска Mac восстанавливаются только ранее разрешенные службы; не создаются новые туннели и не запускаются команды.
- Чистая macOS 14+ Apple Silicon без Homebrew.

Примечание: перед реализацией измерить штатное поведение reconnect самого tunnel-client и уточнить значения его GET /health. Не следует рестартовать исправный клиент из-за краткого сетевого сбоя.
