# McpGo Reliability 2.0 — устойчивые задания и браузерные действия

Этот документ описывает реализованные меры надёжности. Идеи длительных job, readback результата и принципа «не повторять неизвестную запись» сопоставлены с [Pomerado](https://github.com/Pomerado/pomerado); исходный код McpGo реализован самостоятельно. Pomerado не является runtime-зависимостью.

## 1. Задача и гарантии

ChatGPT может потерять поток ответа, пока Mac продолжает выполнять тесты или браузерную операцию. Нельзя автоматически повторять команду, если возможен побочный эффект. Поэтому McpGo различает состояния:

| Состояние | Значение | Разрешено |
|---|---|---|
| queued/starting | Команда зарегистрирована, подтверждения выполнения ещё нет | Проверять статус |
| running | Worker работает, публикует heartbeat и progress | Читать статус и логи |
| exited | Получен окончательный exit receipt | Получить сохранённый результат |
| cancelled | Получено подтверждение завершения после запроса отмены | Проверить внешние эффекты |
| unknown | Runner исчез без достоверного завершения | Readback, **не повторять автоматически** |
| launch_error | Команда не смогла стартовать | Анализировать spawn error |

Это **at-most-one dispatch attempt** при использовании стабильного ID, а не гарантия exactly-once внешнего результата.

## 2. Durable job: жизненный цикл

```text
job_start(command, request_id)
    │ exclusive ID claim → job_id
    │ request.json/status.json, stdout.log/stderr.log
    ▼
detached job_worker → zsh (до 4 часов)
    ├── heartbeat каждые 5 секунд
    ├── progress: [MCPGO_PROGRESS] JSON
    ├── stdout/stderr, первые 64 MiB каждого потока
    ├── cancel.json → SIGTERM → SIGKILL при необходимости
    └── result.json (контрольные суммы) → terminal status

job_recent → job_watch/job_status → job_result/job_output
```

По умолчанию файлы живут в `~/Library/Application Support/ChatTerminalHub/OneShotJobs/`, **не** в Git-репозитории. Тесты изолированы через `MCPGO_JOB_ROOT`.

## 3. Idempotency и повторное подключение

`job_start` принимает опциональный `request_id` длиной 8–128 символов (латиница, цифры, `._:-`). Пример:

```json
{"command":"pnpm test","cwd":"/absolute/path/to/repository","timeout_ms":1200000,"request_id":"integration-tests-2026-11-08"}
```

Повтор той же комбинации ID, команды, рабочего каталога и timeout возвращает **исходный** `job_id` и `deduplicated:true`. Другая команда с прежним ID отвергается (`REQUEST_ID_CONFLICT`). Вызов с уже зарегистрированным ID никогда не выполняет команду повторно.

ID резервируется атомарным файлом с эксклюзивным созданием **до** запуска процесса. Если процесс упал после резервирования, но до записи job, возвращается `unknown`, а не ложный повтор.

## 4. Восстановление после обрыва ChatGPT

1. Предпочитайте `job_start` для длинных тестов, сборок и иных непомещающихся в короткий MCP-ответ операций.
2. Сохраните `job_id`. После потери ответа используйте **`job_recent({limit:10})`**: только метаданные, без текста команды.
3. Ожидайте обновления `job_watch({job_id,wait_ms:15000})` (максимум 25 секунд), без активного частого polling.
4. Проверяйте `job_status`: heartbeat, последнюю дату вывода, bytes, структурированный progress и флаг stale heartbeat.
5. Только после окончательного `state=exited, exit_code=0, timed_out=false, spawn_error=null` объявляйте PASS.
6. `job_result` возвращает итоговые данные, `job_logs` — ограниченный хвост, `job_output` — точные страницы большого вывода.

Если job оказался `unknown`, **не** интерпретируйте это как FAIL без побочных эффектов или как PASS.

## 5. Прогресс и сохранность результатов

Команда может по желанию печатать однострочный маркер:

```text
[MCPGO_PROGRESS] {"percent":42,"stage":"Unit tests"}
```

Worker сохраняет только `percent` (0–100), `stage` (не более 120 символов) и время прогресса. Отсутствие маркеров не означает зависание.

Файлы `stdout.log`/`stderr.log` сохраняют первые **64 MiB** на поток. При превышении ограничение обозначается `stdout_truncated`/`stderr_truncated`. В `result.json` фиксируются retained length, SHA-256 содержимого, окончательное состояние, exit code, duration и counters. Итоговый receipt записывается **до** публикации терминального статуса.

`job_output({job_id,stream:"stdout",offset:0,max_bytes:16000})` возвращает `data_base64`, `next_offset`, `has_more` и `retained_bytes`. Base64 сохраняет точность UTF-8 на границах страниц. Для следующей страницы используйте полученный `next_offset`, а не запускайте команду заново.

`job_cancel({job_id})` лишь фиксирует запрос отмены. Финальное `cancelled` можно считать подтверждённым только после завершения процесса. Сделанные командой записи отмена не откатывает.

## 6. Общий Chrome: безопасное исполнение

`playwright/restricted-proxy.mjs` по-прежнему использует личный Chrome через CDP и общую upstream MCP-сессию. Теперь браузерные `tools/call` выполняются **последовательно** в очереди, максимум 16 ожидающих вызовов. Если HTTP-клиент отключился до своего хода, его запрос не должен выполняться после отключения.

Мутирующие действия в одном JSON-RPC batch запрещены. Инструмент `browser_run_code_unsafe` остаётся заблокированным. Это не полноценная межагентская изоляция: пользовательские вкладки и авторизация Chrome по-прежнему общие, а другие пути управления Chrome могут менять его состояние.

### Стабильный browser action ID

Для клиентов, поддерживающих новые заголовки:

```text
x-mcpgo-action-id: unique-client-action-identifier
x-mcpgo-expected-url: https://example.com/exact/page
```

При наличии второго заголовка прокси выполняет read-only `browser_evaluate` и подтверждает точный URL **активной вкладки непосредственно перед действием, внутри общей блокировки**. Если адрес отличается или не может быть подтверждён, запись не отправляется (HTTP 409). Между этой проверкой и последующим кликом другие MCP browser-tool calls не выполняются.

Затем журнал `playwright/action-guard.mjs` сохраняет `dispatched` с записью owner-only **до** обращения к браузеру. Повтор `x-mcpgo-action-id` не исполняется (HTTP 409), в том числе после перезапуска прокси. Для readback доступен MCP-tool `mcpgo_action_status({request_id})`.

| Receipt | Интерпретация |
|---|---|
| not_found | Запись в **этом** журнале не найдена; это не глобальное доказательство отсутствия действия |
| dispatched | Команда могла быть передана, итог ещё неизвестен |
| completed | Browser MCP вернул HTTP 200, **не гарантия записи на сайте** |
| unknown | Ответ потерян; побочный эффект возможен, повтор запрещён |
| conflict | Тот же ID использован с другими аргументами |

В journal сохраняются **только имя инструмента, хеш ID, SHA-256 аргументов, время и статусы**, не сами URL, пароли, DOM, скриншоты или тексты сообщений. Хранилище `~/Library/Application Support/McpGo/browser-actions/`. Для тестов: `MCPGO_ACTION_ROOT`.

**Защита от повторов действует лишь для вызовов со стабильным action ID.** Обычные browser-tools без этого заголовка остаются разрешены и не становятся exactly-once.

## 7. AutoSend

Перед реальным `browser_click` AutoSend уже сохраняет durable `click-committed`. Теперь дополнительно записывает `actionId = autosend:<UUID>` в своё существующее состояние, а запрос к Safe Proxy передаёт и ID, и **точный URL разговора**. Если вкладка поменялась, прокси отклоняет действие до клика.

После возможной отправки планировщик не повторяет Send: он выполняет read-only `verifying` и при неоднозначности сообщает `unknown`. Потеря HTTP-ответа или рестарт McpGo не должны приводить к двойной отправке.

Автоматическое восстановление явно прерванного ответа ChatGPT остаётся самостоятельным механизмом. Оно может восстановить вкладку и поставить **новое** пользовательское сообщение, только когда чат подтвердил готовность, а предыдущая попытка не находится в `sending/verifying`.

## 8. Что это НЕ гарантирует

- Нет доступа к внутреннему серверному прогрессу модели ChatGPT. Живой heartbeat процесса на Mac не подтверждает прогресс удалённой модели.
- При выключенном Mac задания не продолжают исполнение. Завершённые receipts сохраняются, незавершённые могут стать `unknown`.
- Если внешнее действие состоялось, но процесс умер до подтверждения, безопасный автоматический повтор невозможен без readback внешней системы.
- Отдельный браузерный вызов сериализован, но другой Chrome/CDP клиент вне прокси или сам пользователь может изменить вкладку в любой момент.
- 64 MiB — явный потолок сохранённых байтов на поток. При превышении `truncated` честно отмечает потерю хвоста.
- Генерация детерминированных MCP-интеграций, свойственная Pomerado, **не включена** в McpGo этим обновлением.

## 9. Изолированные проверки

```bash
node --test terminal/tests/*.test.*
node --test playwright/tests/*.test.mjs
node --test autosend/tests/*.test.mjs
python3 -m unittest discover -s tests -v
python3 -m unittest discover -s messaging/tests -v
```

Тесты запускают отдельный MCP-сервер на случайном локальном порту, используют временные `MCPGO_JOB_ROOT` и `MCPGO_ACTION_ROOT`, а для браузера — fake backend. Рабочие ChatGPT-разговоры и туннели в интеграционных тестах **не используются**.

Тестируются crash-safe idempotency, запрет повторной отправки, cancel с подтверждением, heartbeat, progress, output pagination, long-poll, JSON-RPC routes, сериализация Chrome-действий, восстановление отсутствующего ответа и проверка URL активной вкладки.

Публичный релиз отдельно требует проверки **реального Chrome CDP** и конкретного сценария отправки в специально выделенный тестовый разговор; mock E2E не заменяют этот шаг.

## 13. Восстановление по итоговому receipt и контроль heartbeat (08.11.2026)

Если worker успел атомарно записать `result.json`, но умер до финального обновления `status.json`, вызов `job_status` сначала сопоставляет версию, `job_id`, терминальное состояние и `exit_code` durable receipt. При корректном receipt выводит `RECOVERED_FROM_DURABLE_RESULT`. Это позволяет честно восстановить результат без повторной команды.

Если `status.json` говорит `running/cancelling`, PID ещё существует, но heartbeat не обновлялся более 30 секунд, отображается `stalled` с `RUNNER_HEARTBEAT_STALE`. В частности, случайное повторное использование PID другим процессом не означает живую полезную задачу. `stalled` не является PASS, и автоматическая отмена/повтор такого задания запрещены: сначала проверка логов и внешних эффектов. Повреждённый `result.json` приводит к `unknown`, а не к выдуманному успешному завершению.
